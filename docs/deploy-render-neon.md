# Deploying Daprova on Neon + Render (free tier)

This replaces the expired Railway setup. Database → **Neon**, API → **Render**.
Frontends are handled separately (see "Frontends" at the end).

## Architecture notes that shaped this setup

- The API runs with **`tsx`** (TypeScript directly), not a compiled `node dist`
  build. The 16 DB migrations in `api/migrations/*.ts` are loaded via dynamic
  `import()` at boot and live outside the tsc `rootDir`, so a compiled build
  never produces runnable `.js` for them. `tsx` sidesteps this and matches how
  the app ran on Railway. (`tsx` is therefore a runtime dependency of `api`.)
- Migrations run **automatically on boot** (`runMigrationsToLatest()` in
  `api/src/index.ts`), so a fresh database is schema-migrated on first deploy —
  no separate migration step needed.
- `@daprova/shared` is only imported as `import type`, so it has no runtime
  footprint; `npm install` at the repo root links the workspace for builds.

## Step 1 — Database on Neon

1. Sign up at https://neon.tech (free, no card). Create a project — choose the
   **EU (Frankfurt)** region to match the Render region below.
2. In the project's **Connection Details**, copy the **pooled** connection
   string (host contains `-pooler`). It looks like:
   `postgresql://USER:PASSWORD@ep-xxxx-pooler.eu-central-1.aws.neon.tech/neondb?sslmode=require`
3. Keep `?sslmode=require` on the string. This becomes `DATABASE_URL` on Render.

> If you still have real data locked in Railway, export it first
> (`pg_dump` from Railway's `DATABASE_URL`) and `psql`-restore it into Neon
> before the first API deploy, so boot-migrations apply on top of it.

## Step 2 — API on Render

1. Push this repo to GitHub (Render deploys from a Git repo). The changes that
   must be pushed: `render.yaml`, and the `api/package.json` edits (tsx moved to
   dependencies + `start` script).
2. At https://render.com → **New → Blueprint**, connect the repo. Render reads
   `render.yaml` and proposes the `daprova-api` web service.
3. Fill in the env vars marked `sync: false`:
   - `DATABASE_URL` → the Neon pooled string from Step 1
   - `FIREBASE_API_KEY` → the Firebase Web API key (same value as admin-web's
     `VITE_FIREBASE_API_KEY`)
   - `RESEND_API_KEY` → your Resend key
   - `ADMIN_DASHBOARD_ORIGIN`, `ASSESSMENT_WEB_ORIGIN`, `PLATFORM_WEB_ORIGIN`
     → leave blank for now; set them after the frontends are deployed, then
     redeploy. (Until set, browser calls from the frontends are CORS-blocked.)
   - `SESSION_JWT_SECRET`, `REFRESH_JWT_SECRET`, `BOOTSTRAP_SECRET` are
     auto-generated by Render — no action needed (read `BOOTSTRAP_SECRET` from
     the dashboard when you need to provision the first org).
4. Deploy. Watch logs for `[migrate] ...` lines (migrations applying) then
   `[daprova-api] listening`. Health check is `GET /health`.

**Free-tier caveat:** the service sleeps after ~15 min idle; the next request
cold-starts in ~30-50s. Assessment links opened from email will feel this on
first hit.

## Step 3 — Provision the first org (fresh DB only)

On an empty database, `POST /api/v1/bootstrap` creates the first org + admin. It
requires the `BOOTSTRAP_SECRET` header/body value (from Render) and self-disables
once any organisation exists. See `api/src/routes/bootstrap.ts` for the payload.

## Step 4 — Frontends on Cloudflare Pages

All three frontends are static on Cloudflare: create **three Pages projects**
(Workers & Pages → Create → Pages → Connect to Git), all pointing at this repo.
Leave **Root directory** blank (repo root) for each, so `npm install` uses the
root `package-lock.json` and links the workspaces.

| Project | Build command | Output directory | Build env vars |
|---|---|---|---|
| admin-web | `npm run build --workspace=admin-web` | `admin-web/dist` | `VITE_API_BASE`, `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_PROJECT_ID`, `VITE_ASSESSMENT_WEB_ORIGIN` |
| assessment-web | `npm run build --workspace=assessment-web` | `assessment-web/dist` | `API_BASE_URL` |
| platform-web | `npm run build --workspace=platform-web` | `platform-web/dist` | `API_BASE_URL`, `ADMIN_WEB_ORIGIN`, `FIREBASE_API_KEY`, `FIREBASE_PROJECT_ID` |

- `VITE_API_BASE` / `API_BASE_URL` = the Render API URL, e.g.
  `https://daprova-api.onrender.com` (no trailing slash).
- Every var is baked in **at build time** — change one, then retry the
  deployment. Builds fail on purpose if any listed var is missing.
- Set `NODE_VERSION=20` on each project to match CI.
- Routing: admin-web ships no `404.html`, so Pages serves `index.html` for
  client-side routes automatically. assessment-web's `_redirects` maps
  `/assess/*` and `/satisfaction/*` to the app shell.
- `assessment-web/server.js` and `platform-web/server.js` are now dev-only;
  `build.mjs` in each writes the same `/config.js` statically.

### Then wire the API to the frontends

1. On Render, set `ADMIN_DASHBOARD_ORIGIN`, `ASSESSMENT_WEB_ORIGIN`,
   `PLATFORM_WEB_ORIGIN` to the exact Pages URLs (e.g.
   `https://daprova-admin.pages.dev`, no trailing slash) and redeploy.
2. Firebase Console → Authentication → Settings → **Authorized domains**: add
   the admin-web and platform-web domains, or login fails silently.
3. `COOKIE_SAMESITE=none` (set in `render.yaml`) is required while the
   frontends are on `*.pages.dev` and the API on `*.onrender.com` — they are
   different sites. Safari still blocks third-party cookies, so there a page
   reload logs the user out. The real fix is a custom domain for everything
   (`app.daprova.com`, `learn.daprova.com`, `api.daprova.com`); then set
   `COOKIE_SAMESITE=lax`.
4. Only the Pages **production** URL is in the CORS allowlist; preview
   deployments (`<hash>.<project>.pages.dev`) will be CORS-blocked.

### Why the API isn't on Cloudflare too

It's an Express server on Node with `pg`, `pdfkit`/`docx` report generation,
file-based fonts and boot-time migrations. Moving it to Workers would be a
rewrite, not a config change — it stays on Render.
